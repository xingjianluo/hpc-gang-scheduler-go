# hpc-gang-scheduler-go

进程内的 HPC 整组（gang）作业调度组件。用模拟节点与资源池代替真实集群，
不依赖任何外部集群服务或凭据，覆盖 **整组调度、配额、优先级抢占、资源回填、
任务重试、执行超时、节点失联恢复** 完整链路。

## 结构

```
scheduler/            核心调度器包
  types.go            作业/任务/资源/事件等类型定义
  node.go             模拟计算节点（容量 + 已用账本）
  scheduler.go        提交校验、整组调度、抢占、回填、事件处理、恢复
  store.go            JSON 快照持久化（临时文件 + rename 原子写入）
  scheduler_test.go   整组拒绝 / 并发竞态 / 抢占 / 节点失联重复事件 / 恢复测试
  gang_ops_test.go    整组超集群拒绝 / 失联整组回退 / 跨实例迟到事件去重测试
cmd/demo/             本机可运行的端到端演示
```

## 调度语义

- **整组（gang）调度**：一个作业（`Count>1` 即作业数组）的全部任务必须在同一轮
  调度中都找到节点才一起启动；放不下就整组留在队列，绝不部分启动占用资源。
- **整组拒绝**：提交时校验失败即整组拒绝，原因可区分（`RejectReasonOf(err)`），
  被拒绝的作业不会留在队列里占位：
  - `DUPLICATE_SUBMISSION`：同一 `JobID` 重复提交；
  - `RESOURCE_NEVER_FITS`：单任务需求超过所有节点容量（永远调度不上，直接拒绝）；
  - `GANG_EXCEEDS_CLUSTER`：单任务都放得下，但整组需求超过整个集群的物理上限。
    判定方式是把全部节点（含暂时失联的，失联视为可恢复）容量清零后，用与正式
    调度相同的 first-fit 算法在“空集群”上试放整个作业组；试放失败即永远排不上。
    节点规格不一致时按真实安置结果判断，而不是只看最宽节点或资源总量
    （例如 8+4 的集群里 2×6 的整组总量 12 看似不超，实际第二个任务无处可去）；
  - `QUOTA_EXCEEDED`：提交方在途资源（排队+运行+待重放）加上新作业超出配额。
- **队列排序**：优先级数值大者优先，同级按提交时间先到先排。
- **回填**：队首作业整组放不下时跳过它继续看后面的作业，小作业可以穿插启动。
- **单任务重放**：运行中作业里失败重试 / 被抢占的任务，
  在每轮调度开始时按优先级单独安置（`REPLACE` 日志）。
  节点失联触发的整组回退不走这条路径，而是整组退回队列按 gang 语义重新拉起。

## 配额与抢占规则

- 配额按提交方（`Owner`）计，统计该方所有未终态作业中未终态任务的资源总和；
  提交时 `已在途 + 新申请 > 配额` 即整组拒绝。
- 高优先级作业整组放不下时，从 **优先级严格更低且标记 `Preemptible`** 的运行中
  任务里按优先级从低到高挑选受害者；**只有抢占后整组确实能放下才真正驱逐**，
  否则不做无谓抢占（试算失败会回滚账本）。
- 被抢占任务回到待调度状态（`PREEMPTED`），节点账本同步归还，不消耗重试次数；
  资源空出后在后续调度轮次自动回填。
- 一个任务彻底失败（重试次数耗尽或超时）即整组终止：其余任务被杀、资源释放，
  作业进入 `FAILED`。

## 事件与状态恢复

- 外部事件（任务完成 / 节点失联 / 节点恢复）允许 **重复或乱序** 到达：
  - 已到终态的任务收到完成通知直接忽略，不重复计数；
  - 非 `RUNNING` 状态任务（如节点失联后已重入队）的迟到通知按 stale 忽略；
  - 重复的节点失联/恢复事件幂等。
- **跨实例去重（运行代数）**：任务每次（重新）安置到节点时 `Generation` 递增。
  完成/失败通知可携带 `Event.Generation` 标识它来自任务的第几代运行实例：
  - `Generation>0` 且与任务当前代数 **不相等** 时一律忽略——这覆盖任务被抢占或
    节点失联重排之后，上一轮已被驱逐实例发来的迟到通知，既不能用它把当前这一轮
    判成完成或失败，也不会让完成计数翻倍；作业成败只按当前运行轮次判定；
  - `Generation=0`（未指定）保持既有语义：只按任务当前状态判断（兼容旧调用方）。
- **节点失联整组回退**：节点失联时，凡有运行中任务落在该节点上的作业，
  其在健康节点上的同伴也一起停下，整组退回队列等待（`GANG ROLLBACK` 日志），
  不出现同一作业一半在跑、一半在等。回退不消耗任务重试次数（`Attempt` 不变），
  健康节点的账本同步归还；已终态（如已成功）的任务保持原状不重跑。
  资源足够后整组重新拉起，只重跑未完成的任务；节点恢复后重新参与调度。
- 执行超时：`ExecTimeout>0` 的任务超时时按失败处理（走重试/整组终止逻辑）。
- 持久化：每次状态变更后把作业与节点账本快照原子写入 `Store`；
  进程重启后 `Recover()` 从快照恢复——运行中的任务保持运行、排队作业重新入队，
  调度从断点继续而不是从头开始。

## 并发安全

所有导出方法共用一把互斥锁，并发提交、并发调度、并发事件下同一资源不会被
重复分配；测试在 `-race` 下验证账本永不超过节点容量、账本与运行任务占用一致。

## 兼容范围

- 不携带 `Generation` 的事件（`Generation=0`）按既有状态机处理，旧调用方无需修改；
  只有显式携带代数的事件才启用跨实例去重。
- 节点失联语义由“只重排落在失联节点上的任务”变更为“整组回退”：依赖旧的部分
  重排行为的调用方需要留意，现在同一作业在健康节点上的同伴也会被停下重排。
- 新增 `GANG_EXCEEDS_CLUSTER` 拒绝原因后，过去会永久挂在队列里的“整组超集群
  上限”作业现在会在提交时被拒绝；`Submit` 返回的错误仍可用 `RejectReasonOf` 区分。
- 持久化快照新增 `Task.Generation` 字段，旧快照缺少该字段时按 0 处理，
  恢复后第一次重新安置会自然递增，不影响恢复流程。

## 本地验证

```bash
go build ./...          # 编译
go test ./...           # 单元测试（日志含调度决策与资源账本快照）
go test -race ./...     # 竞态检测
go test -run TestGangExceedsClusterReject -v ./scheduler/        # 整组超集群拒绝
go test -run TestNodeLossGangRollbackPartialRestart -v ./scheduler/  # 失联整组回退
go test -run TestStaleInstanceEvents -v ./scheduler/             # 跨实例迟到事件去重
go run ./cmd/demo       # 端到端演示：提交→抢占→失联整组回退→回填→状态恢复
```
