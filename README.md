# hpc-gang-scheduler-go

进程内的 HPC 整组（gang）作业调度组件。用模拟节点与资源池代替真实集群，
不依赖任何外部集群服务或凭据，覆盖 **整组调度、配额、优先级抢占、资源回填、
任务重试、执行超时、节点失联整组回退、跨实例事件去重** 完整链路。

## 结构

```
scheduler/            核心调度器包
  types.go            作业/任务/资源/事件等类型定义
  node.go             模拟计算节点（容量 + 已用账本）
  scheduler.go        提交校验、整组调度、抢占、回填、事件处理、恢复
  store.go            JSON 快照持久化（临时文件 + rename 原子写入）
  scheduler_test.go   整组拒绝 / 并发竞态 / 抢占 / 节点失联重复事件 / 恢复测试
  gang_features_test.go 整组超上限拒绝 / 失联整组回退 / 跨实例迟到事件测试
cmd/demo/             本机可运行的端到端演示
```

## 调度语义

- **整组（gang）调度**：一个作业（`Count>1` 即作业数组）的全部任务必须在同一轮
  调度中都找到节点才一起启动；放不下就整组留在队列，绝不部分启动占用资源。
- **整组拒绝**：提交时校验失败即整组拒绝，原因可区分（`RejectReasonOf(err)`）：
  - `DUPLICATE_SUBMISSION`：同一 `JobID` 重复提交；
  - `QUOTA_EXCEEDED`：提交方在途资源（排队+运行+待重放）加上新作业超出配额；
  - `RESOURCE_NEVER_FITS`：单任务需求超过所有节点容量（永远调度不上，直接拒绝）；
  - `GANG_EXCEEDS_CLUSTER`：单任务都放得下，但整组总量超过整个集群的物理上限。
    判定是精确的：整组任务规格相同，每个节点的容纳数 = 各资源维度
    `floor(容量/需求)` 的最小值，全部节点求和即为集群上限——异构节点下不会
    只盯着最宽的节点误判（例如 8+4 CPU 的集群跑 2 个 6 CPU 任务，总量 12<=12
    看似够，实际只有 1 个能放下，照样拒绝）。按物理容量计算，与节点当前是否
    失联、已被占用多少无关。
- **队列排序**：优先级数值大者优先，同级按提交时间先到先排。
- **回填**：队首作业整组放不下时跳过它继续看后面的作业，小作业可以穿插启动。
- **单任务重放**：运行中作业里失败重试 / 被抢占的任务，
  在每轮调度开始时按优先级单独安置（`REPLACE` 日志）。

## 配额与抢占规则

- 配额按提交方（`Owner`）计，统计该方所有未终态作业中未终态任务的资源总和；
  提交时 `已在途 + 新申请 > 配额` 即整组拒绝。
- 高优先级作业整组放不下时，从 **优先级严格更低且标记 `Preemptible`** 的运行中
  任务里按优先级从低到高挑选受害者；**只有抢占后整组确实能放下才真正驱逐**，
  否则不做无谓抢占（试算失败会回滚账本）。
- 被抢占任务回到待调度状态（`PREEMPTED`），节点账本同步归还，不消耗重试次数；
  资源空出后在后续调度轮次自动回填。
- 一个任务彻底失败（重试次数耗尽或超时）即整组终止：其余任务被杀、资源释放，
  作业进入 `FAILED`。

## 事件与状态恢复

- 外部事件（任务完成 / 节点失联 / 节点恢复）允许 **重复或乱序** 到达：
  - 已到终态的任务收到完成通知直接忽略，不重复计数；
  - 非 `RUNNING` 状态任务（如已回退重排队）的迟到通知按 stale 忽略；
  - 重复的节点失联/恢复事件幂等。
- **跨实例去重（实例代次）**：任务每次被拉起（首次调度、重试、抢占后重排、
  失联回退后整组重启）`Generation` 都递增。执行层上报事件时携带它看到的代次
  （`Event.Generation`）：非 0 且与任务当前代次不一致即判为旧实例的迟到通知，
  直接忽略——即使任务已在新一代重新运行，旧实例的完成/失败也不会改判当前轮；
  作业最终成败以当前运行代次上报的结果为准。
  **兼容范围**：`Event.Generation` 为 0 表示上报方不跟踪代次，退化为仅按任务
  状态判断（既有行为不变）；持久化快照中旧记录没有 `Generation` 字段时按 0
  恢复，首次拉起后正常递增。
- **节点失联整组回退**：节点失联时，凡有任务落在该节点上的作业 **整组回退**——
  健康节点上的同伴任务也一起停掉（账本同步归还），全部未终态任务回到
  `PENDING`，作业重新排队（`GANG ROLLBACK` 日志），等资源够了再整组拉起，
  不会出现同一作业一半在跑、一半在等。回退不消耗任何任务的重试次数；
  已终态（成功）的任务保持终态，整组重启时只重跑未完成的任务。
  节点恢复后重新参与调度。
- 执行超时：`ExecTimeout>0` 的任务超时时按失败处理（走重试/整组终止逻辑）。
- 持久化：每次状态变更后把作业与节点账本快照原子写入 `Store`；
  进程重启后 `Recover()` 从快照恢复——运行中的任务保持运行、排队作业重新入队，
  调度从断点继续而不是从头开始。

## 并发安全

所有导出方法共用一把互斥锁，并发提交、并发调度、并发事件下同一资源不会被
重复分配；测试在 `-race` 下验证账本永不超过节点容量、账本与运行任务占用一致。

## 本地验证

```bash
go build ./...          # 编译
go test ./...           # 单元测试（日志含调度决策与资源账本快照）
go test -race ./...     # 竞态检测
go test -run TestNodeLossGangRollbackRestart -v ./scheduler/   # 失联整组回退的决策日志
go test -run TestCrossInstanceStaleEvents -v ./scheduler/      # 跨实例迟到事件去重
go test -run TestGangExceedsClusterRejected -v ./scheduler/    # 整组超集群上限拒绝
go run ./cmd/demo       # 端到端演示：提交→抢占→失联整组回退/恢复→回填→状态恢复
```
